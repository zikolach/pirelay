# Messenger conversations in PiRelay

Telegram, Discord and Slack can all carry a question and an answer. What differs is **how the human's reply is associated with the question**. A normal prompt targets a session; a Telegram guided answer can target a particular turn; an approval targets a particular pending operation. These are not interchangeable.

## One remote turn

1. The messenger runtime receives a message, checks the sender and resolves an authorized binding and target session. In Telegram the normal factory creates a broker: `extensions/relay/adapters/telegram/runtime.ts:2716`. The broker requests `deliverPrompt` from the session-owning client (`extensions/relay/broker/process.js:1687`, `extensions/relay/broker/tunnel-runtime.ts:283`). The in-process Telegram runtime is a separate implementation, not evidence that a broker change works. Discord and Slack call the route directly (`extensions/relay/adapters/discord/runtime.ts:1090`, `extensions/relay/adapters/slack/runtime.ts:887`).
2. `deliverRoutePrompt` probes the live route, records the requester and calls the route's `sendUserMessage`. An idle session receives an ordinary user message; a busy one receives `followUp` or `steer`. If submission throws, the previous requester state is restored. A failure in the *post-submission* hook does not undo the Pi message (`extensions/relay/core/route-actions.ts:113`). A messenger acknowledgement is therefore not a terminal result, nor is retrying a failed acknowledgement necessarily safe.
3. The route calls `pi.sendUserMessage` in the live extension context (`extensions/relay/runtime/extension-runtime.ts:890`). On `agent_end`, the extension extracts final assistant text, falling back to completed message text, assigns a turn ID, and derives structured-answer metadata from the output. An abort takes precedence; otherwise a turn without final text is reported as failed (`extensions/relay/runtime/extension-runtime.ts:2183`, `:2235`, `:2240`).
4. The extension publishes route state and fans terminal notifications out to configured runtimes (`extensions/relay/runtime/extension-runtime.ts:2261`). Each runtime determines its delivery destination; this is session notification fan-out, not a reply RPC to the inbound message. Telegram's broker path registers the completed summary and sends to the bound chat (`extensions/relay/adapters/telegram/runtime.ts:2748`); Discord and Slack have their own completion handlers (`extensions/relay/adapters/discord/runtime.ts:174`, `extensions/relay/adapters/slack/runtime.ts:210`). Slack also remembers the originating thread on idle submission (`extensions/relay/adapters/slack/runtime.ts:891`).

## When Pi asks the human

| Path | What the human does | What Pi receives |
| --- | --- | --- |
| Telegram structured clarification | Chooses a button, enters a custom choice or walks through a draft based on the latest completed output. The runtime can ask about an ambiguous reply rather than guessing. | A new user message containing the interpreted answer. Draft steps and cancellation need not submit anything. The custom-answer path checks expiry and turn identity first (`extensions/relay/adapters/telegram/runtime.ts:2088`, `:2190`, `:2214`; broker counterpart `extensions/relay/broker/process.js:1571`, `:2181`). |
| Discord or Slack clarification | Replies in the bound conversation. There is no corresponding guided-answer dispatcher on the ordinary bound-message path. | The reply text is a new prompt addressed to the selected route, not a decision keyed to an outstanding question (`extensions/relay/adapters/discord/runtime.ts:1090`, `extensions/relay/adapters/slack/runtime.ts:880`). A reply in the same thread provides conversational context, not proof of which turn was answered. |
| Tool approval on any of the three | Uses an approval command or action carrying an approval ID. | A decision for a waiting tool gate, **not** a user prompt. The host checks the stored request, session, pending status, expiry, requester and current binding. Requester matching includes channel, instance, conversation, user and thread (`extensions/relay/runtime/extension-runtime.ts:794`, `:838`). A plain “yes” to a clarification must not grant tool permission. |

## Priorities and next change

1. **First: specify the clarification reply contract before sharing UI.** Use one question with two choices and an explicit free-text fallback. Keep the originating session, turn and requester address together. Reject a stale explicit choice after a newer turn or route switch; never reinterpret it as a fresh prompt. An unrelated unquoted message must still work as an ordinary prompt.
2. **Next: prove destination and submission semantics.** Exercise two bound sessions, two users, and a Slack thread. Assert *which route received what, how many times, and where the reply went*; do not just assert notification wording. Include a busy follow-up so an earlier completion cannot be mistaken for its result.
3. **Keep approval separate.** Preserve the pending-operation lookup and authorization on both text and button paths. Do not use guided-answer parsing to resolve approvals, or infer authorization from a displayed button.

**Scoped next focus:** one test-first Slack threaded choice reply, using Telegram's existing choice behavior as the reference (`tests/answer-workflow.test.ts:93`, `tests/runtime.test.ts:1789`, `tests/broker-process.test.ts:573`). Pass when the intended human's current choice submits exactly one answer to the original session, a replay or wrong-thread action submits none, and ordinary thread text still follows normal prompt delivery. Leave Discord controls, multi-question drafts, transport refactoring and approval persistence out of that slice.
